# askdnd v2

A companion app for one D&D 2024 table (4 players + DM, playing on Zoom with D&D Beyond). It does three things: a **pre-session refresher** (story recap plus character briefing), **campaign memory** built from session transcripts, and **rules answers** that cite book pages. ## Privacy and data rules (important)
- **Raw transcripts never go to a cloud service or into the database.** They're filtered locally (Ollama) on Brett's Mac first, and only the filtered game content is sent. That **cleaned transcript is kept in file storage** (S3 `v2/files/`, encrypted; `GameSession.transcript_key`; Brett, Nov 7), never in the database, shown on no page, read only by Claude when drafting; an admin can let it go (the nightly sweep deletes it). Who talked leaves the Mac as seconds per speaker name only.
- **The repo is public** (Brett, Nov 9; private again later): never commit book text or Monster Manual stat blocks, players' writing, email addresses or the table's real names (roles, or made-up names in tests); the party's D&D Beyond sheets only locked (`scripts/fixtures.py`). tests/test_public_safe.py fails on any of it.
- **Never commit** `.env*`, transcripts, campaign notes, character notes, or exports. Campaign data lives in the database, not in git. Keep `.gitignore` strict (`transcripts/`, `private/`, `*.docx`, `.env*`).
- **Hidden is as if it didn't exist** (Brett, Nov 6): a hidden World entry (status draft), its facts and relationships never go to Claude (drafts, questions, suggestions, descriptions, conversations), drafts never link to it, and the table never sees its name anywhere, a key moment included, until the DM shows it. tests/test_extraction.py guards it.
- Visibility: **character notes are visible to players but NOT the DM.** Everything else is visible to everyone at the table. Exceptions, visible to everyone including the DM (Brett, 2026-10-17): a character's **D&D Beyond Background tab and backstory** (personality traits, ideals, bonds, flaws, appearance, backstory) and players' **item notes on D&D Beyond**. The rest of D&D Beyond's Notes tab (allies, enemies, organizations, other notes) is never stored. None of the player's writing goes into test fixtures or git (item notes live only in `character_item_notes`; `scripts/ddb_fixture.py` strips traits and notes).
- Set and respect a monthly spend limit on the Anthropic API.

## Product rules
- **Inform, don't advise.** Explain what a player has and how it works, including action, bonus action and reaction options. Never tell them what to do.
- **The DM makes every ruling.** Rules answers inform the DM and players; they don't decide.
- 2024 rules (PHB, DMG, MM) only. Label official clarifications vs. community opinion, and exclude 2014-rules discussion.
- Characters and NPCs can be renamed (e.g. Sarkas → No Name), so model names with aliases.
- AI-drafted recaps are reviewed by Brett before the table sees them; his corrections feed future extractions (glossary + correction log).

## Conventions
- **Robust** (Brett, Nov 13): an enhancement may need tweaking, but it never has a negative impact on what already works, now or later: no new bug (in code or in the tests), no workflow left incomplete, no UI or UX quietly made worse. docs/plans/2026-11-13-engineering-practices.md › What robust means maps each to the checks that catch it. **Before merging anything people see, run `uv run python scripts/visual_compare.py`** (foundation F7: every main page before and after, private/visual/report.html; a new state a page only shows sometimes gets a picture in tests/browser/test_pictures.py) and look at every changed page: only what was asked for may change. **Before merging any pull request, run the code review at high effort on its diff** (`/code-review high <PR>`), fix what it finds or say why not, and fill in the pull request's Robust and Review sections (.github/pull_request_template.md).
- **Before calling a change done** (Brett, Nov 7: askdnd is live; follow the design system and solve the whole problem, whatever it costs in tokens). Today's misses are the reason: Your notes ignored View as, and its tabs were hand-built instead of the tab bar.
  1. **The design system first**: build from docs/DESIGN.md and Manage › askdnd › Design system (`/manage/design`: the tab bar, pills, windows, lists, corner cards, tiles). A piece that isn't there is added there, not made one-off on a page.
  2. **Every person**: a player (their own character and someone else's), the DM, a reviewer, an admin, **View as** (shows the viewed person's things and changes nothing for them), signed out, a test account.
  3. **Every place it shows**: phone and computer (look at both), each page with the same thing, the side panel, Party, askdnd's table, and other open pages through the live connection.
  4. **Every state**: nothing yet, a lot, long words, D&D Beyond out of reach, a fight running, staging.
  5. **Everything that pointed at it**: links and old addresses, Help (About, FAQ), the DM guide, the tour, CLAUDE.md and docs/MAP.md, the roadmap.
  6. **Look at it yourself** in the browser before Brett does, and tell him what was checked and what couldn't be.
- Small, focused commits with clear messages. Run `uv run ruff check app scripts tests transcript_filter` and `uv run pytest -q` before committing. Ruff's rules (pyproject.toml, foundations F4) catch likely bugs, not style: a date a person sees is the table's (`config.table_today()`, never `date.today()`, the server's clock is UTC), and eval, SQL text and `Markup` only with a `noqa` where the input is checked. app.js, app.css and the templates are linted too (tools/lint: ESLint and Stylelint, run with `npm ci --prefix tools/lint` then `tools/lint/node_modules/.bin/eslint -c tools/lint/eslint.config.mjs app/static` and `…/stylelint --config tools/lint/stylelint.config.mjs "app/static/**/*.css"`; djLint, `uv run djlint app/templates --lint`): no name in app.js shadows another, and every `<button>` says its `type` (inside a form, a button without one submits it). GitHub Actions runs both on every push (Server tests, with branch coverage that mustn't drop under 90% and a table of it on the run's summary page; and Browser tests in three parts side by side, layout, extension and flows, gathered into the one "Browser tests" check), and Railway waits for them before deploying beta. **main is protected** (GitHub Pro, 2026-11-02): a pull request merges only once both pass on a branch up to date with main, for admins too, so a merge Brett approves waits for green (auto-merge is on). Tests run in parallel (pytest-xdist, `-n auto`): each worker has its own test database, so tests must not depend on each other's order; browser tests run a file per worker side by side (its own server and database; tests/conftest.py groups them, and a long file in `SPREAD` spreads its cases), 9 minutes down to about 1.5 (Nov 13); on GitHub a skipped test fails the run.
- **Refusals** (tests/test_refusals.py; Brett, 2026-11-05): every route that changes something is asked, from the app's own list, by someone signed out, a player about another's character and the DM's pages, and another campaign's DM, with a body that passes its form; the database must not change. - **Flaky tests** (Brett, Nov 9: "it often seems like a setup issue instead of a bug"): a browser test that fails is tried once more before it fails the run (pytest-rerunfailures, from tests/browser/conftest.py; server tests stay strict, they've never flaked), and GitHub lists each second try on the run's summary page ("passed only on a second try"). Referencing text is fragile and should not be done."): every piece code or a test refers to has a marker (`data-*`, an id) or a key in the data, and no test, app.js or Python logic matches the words people see (a roll's key, not its label "Initiative"; a page's key, not "Sessions"). tests/test_no_text_refs.py counts the older references and only lets them go down (its BASELINE is the work left). - **Tests read what things are, not their words or places** (Nov 13, the test foundations): the menu bar marks each menu `data-door` and each item `data-item` (a Manage page's key, else notes, dice, feedback, help, tour, signout, dm-tools…), and the Live pill its `data-tone`; tests/menu.py (`door`, `items`, `tone`) reads them from HTML and tests/browser/pages.py (`click_item`, `open_door`, `wait_tone`) drives them in a browser. A new menu item gets a `data-item`; a test checks words only where the words are the point.
- **Browser tests** (tests/browser, Playwright; VTT 0.8): a real server and real Chromium pages, several people at once (`people("player", "dm")`). **Every browser test fails on a page error it didn't expect** (an error the page didn't catch, a console error, an answer of 400 or more; tests/browser/conftest.py `people`, each error tagged with where it came from and an uncaught one's stack): a test that causes one on purpose says so with `person.allow("part of its words")`. A test run holds a lock on its database name, and a second run at the same time steps aside to a name of its own (`…_2`), so runs never drop each other's tables (2026-11-02: what made browser tests flaky). Sessions working in parallel still each use their own local test database (`TEST_DATABASE_URL=postgresql+psycopg://localhost/askdnd_test_<name>`; the browser tests add `_browser`), never run `scripts/pull_beta.sh` while another session's server uses `askdnd_beta`, and preview on a port other than 8000.
- A route that reads its body and uses the database is a plain `def` taking `body=web.JsonBody` or `form=web.FormBody`, not `async def`: a plain route runs on a worker thread, so its database work never holds up the live connections on the server's one event loop. **Nothing on the event loop waits for the database pool** (Sentry ASKDND-V2-P, Nov 8: worker threads hand connections back through the loop, so the loop waiting for one froze the server for 37 seconds): an async route awaiting something else does its database work in `run_in_threadpool`; middleware's access check (`access._rows`) refreshes on a thread, or uses `db.LoopSession` (its own connection). tests/test_event_loop.py fails on an async route that takes `db`.
- **Changes only from askdnd's own pages** (app/same_site.py, foundations F2): a change made with the sign-in cookie whose Origin isn't askdnd's (or Sec-Fetch-Site cross-site) is refused; a client that proves itself another way (the extension's X-Askdnd-Bridge key, X-Feedback-Key, a bearer token) or carries no cookie is left to its route. A new client that isn't a page gets a key of its own, never the cookie.
- **One press, one change; nothing from a CDN; every answer's headers; Undo sealed** (the outside review, Nov 10, `docs/artifacts/outside-review.html`): app.js drops a second press (a submit or click that changes something) of an HTMX element while its first is on its way (typing still queues), so never rely on HTMX queueing a press; scripts the pages run are vendored in `app/static/vendor/<name>-<version>/` with their LICENSE (HTMX, Sortable, Turndown, the dice, html-to-image); app/main.py `SAFE_HEADERS` go on every answer unless its route set its own; what a page hands back for an Undo that the server must trust is signed with `web.seal` and checked with `web.sealed` (a cast's Undo).
- Secrets come from environment variables (Railway variables in production, `.env` locally). Document every variable in `.env.example`.
