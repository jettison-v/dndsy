# askdnd v2

A companion app for one D&D 2024 table (4 players + DM, playing on Zoom with D&D Beyond). It does three things: a **pre-session refresher** (story recap plus character briefing), **campaign memory** built from session transcripts, and **rules answers** that cite book pages. Read these before significant work:

- `docs/BRIEF.md`: what we're building and why (the product)
- `docs/ARCHITECTURE.md`: stack, data, build plan
- `docs/stack.html`: the stack map, a diagram of how the services connect and who changes each one (Claude, Brett, or both), with where every key lives. **Update it** whenever a service, a key or who does what changes, and republish it (its private artifact link is in the file's footer).
- `docs/artifacts/`: the source of every page published on claude.ai (Brett, 2026-10-26: artifacts must outlive Claude). **When you publish a page for askdnd, save its source in the repo** (here, or where it's kept current: `docs/stack.html`, `docs/mockups/`) and add it to `docs/artifacts/README.md`. Public repo: no screenshots of real pages, book text or campaign story.
- `docs/roadmap.html`: **the askdnd Roadmap, the one page Brett reads** for what's happening (Brett, 2026-10-28: plans spread across files and pages were hard to follow): now (with where each piece shows), waiting on, next, parked, later, done, and every plan and mockup with whether it's current. **Update it and republish to its link** (in `docs/artifacts/README.md`) whenever a step's status changes or a plan or mockup is added or superseded; `docs/plans/2026-10-22-vtt-roadmap.md` is the detail behind it.
- `docs/testing-setup.md`: the real-accounts test table on beta (three seats in VTT test). **Keep it current** when a seat, sheet or campaign changes; no email addresses.
- `docs/live-test-plan.md`: the end-to-end test on the real D&D Beyond (`scripts/real_table.py` on the Mac Mini, plus what needs a person). When Brett says "run the live tests", follow it and add a line to its Results. A new bridge feature gets a run.
- `docs/DECISIONS.md`: running decision log. **Append to it** whenever a meaningful decision is made in a session (one line: date, decision, why).

## Privacy and data rules (important)
- **Raw transcripts never go to a cloud service or into the database.** They're filtered locally (Ollama) on Brett's Mac first; only the filtered game content is sent for extraction, and only the extracted story is stored.
- **Never commit** `.env*`, transcripts, campaign notes, character notes, or exports. Campaign data lives in the database, not in git. Keep `.gitignore` strict (`transcripts/`, `private/`, `*.docx`, `.env*`).
- Visibility: **character notes are visible to players but NOT the DM.** Everything else is visible to everyone at the table. Exceptions, visible to everyone including the DM (Brett, 2026-10-17): a character's **D&D Beyond Background tab and backstory** (personality traits, ideals, bonds, flaws, appearance, backstory) and players' **item notes on D&D Beyond**. The rest of D&D Beyond's Notes tab (allies, enemies, organizations, other notes) is never stored. None of the player's writing goes into test fixtures or git (item notes live only in `character_item_notes`; `scripts/ddb_fixture.py` strips traits and notes).
- Set and respect a monthly spend limit on the Anthropic API.

## Product rules
- **Inform, don't advise.** Explain what a player has and how it works, including action, bonus action and reaction options. Never tell them what to do.
- **The DM makes every ruling.** Rules answers inform the DM and players; they don't decide.
- 2024 rules (PHB, DMG, MM) only. Label official clarifications vs. community opinion, and exclude 2014-rules discussion.
- Characters and NPCs can be renamed (e.g. Sarkas → No Name), so model names with aliases.
- AI-drafted recaps are reviewed by Brett before the table sees them; his corrections feed future extractions (glossary + correction log).

## Conventions
- Small, focused commits with clear messages. Run `uv run ruff check app scripts tests` and `uv run pytest -q` before committing. GitHub Actions runs both on every push (two jobs side by side: Server tests and Browser tests), and Railway waits for them before deploying beta. Tests run in parallel (pytest-xdist, `-n auto`): each worker has its own test database, so tests must not depend on each other's order; on GitHub a skipped test fails the run.
- After merging to `main`, run `uv run python scripts/deploy_check.py`: it follows the deploy to beta and rebuilds once or twice when Railway's own build machines fail (our failures it reports, never retries). The backup service rebuilds only when a file it runs changes (its Railway watch paths, `BACKUP_WATCH` in that script; tests/test_deploy.py keeps the list complete, and `--set-backup-watch` copies a changed list to Railway).
- When a feature or a visibility rule changes, update Help's About and FAQ tabs (`app/templates/_help_about.html`, `_help_faq.html`; the page is `/help`) to match. When a campaign-content workflow changes (recaps, entries, suggestions, review), also update the DM guide (`app/templates/dm_guide.html`, Manage › DM guide), which the DM reads instead of the code.
- Tests for core logic (extraction parsing, visibility rules, D&D Beyond parsing). Don't test against live paid APIs by default.
- **Test setup and which tests stay** (2026-10-27): the table's characters, the fake D&D Beyond and signed-in clients are in `tests/table_setup.py`, their fixtures (`admin`, `dm`, `player`, `no_network`) in `tests/conftest.py`; new shared setup goes there, not in a test file (a few older files still share theirs: test_entities, test_suggestions, test_table_rolls). A test that guards one of Brett's standing rules (privacy, who sees what, sign-in, spending) starts its docstring "A standing rule" with where the rule comes from: never retire one. Retire a test when what it guards can't happen any more (a one-time data move beta has run) or another test already catches the same thing.
- **Layout at every width** (docs/DESIGN.md › Narrow screens): tests/browser/test_layout.py checks every main page at 375, 768, 1000 and 1280px for anything that scrolls sideways, spills out of its box, wraps a one-line control or overlaps (tests/browser/layout_check.js). A new page goes in its list. At the end of each roadmap phase, run `scripts/layout_sweep.py` on the local copy of beta and look over its screenshots in private/layout-sweep/.
- **The real extension in tests** (tests/browser/test_extension.py; Brett, 2026-10-30): a persistent Chromium with extension/askdnd-bridge loaded, a stand-in page at D&D Beyond's own address, askdnd as it runs on beta. Use it for anything the extension does between tabs and askdnd. What D&D Beyond itself does (saving, its game log, its VTT) stays for the real accounts in `docs/testing-setup.md`.
- **Browser tests** (tests/browser, Playwright; VTT 0.8): a real server and real Chromium pages, several people at once (`people("player", "dm")`). Add one whenever a flow depends on what pages do: keys, clicks, live updates between people, what one person sees of another's action. They run in `uv run pytest` (Chromium: `uv run playwright install chromium`) and on GitHub. Sessions working in parallel each use their own local test database (`TEST_DATABASE_URL=postgresql+psycopg://localhost/askdnd_test_<name>`; the browser tests add `_browser`), never run `scripts/pull_beta.sh` while another session's server uses `askdnd_beta`, and preview on a port other than 8000.
- A route that reads its body and uses the database is a plain `def` taking `body=web.JsonBody` or `form=web.FormBody`, not `async def`: a plain route runs on a worker thread, so its database work never holds up the live connections on the server's one event loop.
- Secrets come from environment variables (Railway variables in production, `.env` locally). Document every variable in `.env.example`.
