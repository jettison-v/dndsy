Would I build askdnd's backend differently?

You asked: knowing every requirement and limit we know now, would the backend be built differently? A reviewer new to askdnd read the brief, the architecture, the decision log and all the code; I checked its evidence and added what building it taught me. Short answer: the core holds up. What I'd change is where work runs, and one boundary.

How to read it"Plan it" is worth a Roadmap item; "when nearby" is done as part of other work in that code. Nothing here is urgent or broken today: each item says what it costs us now.

Background work runs inside the web app

Plan it
app/main.py starts seven loops; recap drafts run on threads in the web process · medium · low risk
Why it was built this way

No extra service to run or pay for, when askdnd was small.

What I'd do now

One table of jobs in Postgres that a separate worker takes from, one at a time (no Redis: the same database). The worker is the same code with a different start command on Railway.

What shows it hurts

About eight deploys a day since Nov 11 (112 merges), and each one kills a recap draft in progress: a whole step exists only to say "Draft it again". Locks and guards are scattered to stop jobs running twice.

Reading D&D Beyond happens while a page loads

Plan it, after the first
app/characters.py, app/ddb_bridge.py, app/unwatched.py, app/live.py · medium · Careful lane: a live test on the Mini
Why it was built this way

Keep the last good copy of each sheet, and refresh it when someone looks.

What I'd do now

One refresh job per character, done by the worker above, at most so often; a page only asks for a refresh and shows the stored copy.

What shows it hurts

Beta ran out of database connections three times (Nov 2 and Nov 6), and the 37-second freeze on Nov 8 was the same exhausted pool. Four things can trigger a read and they race, which is why rules like "a public read never replaces a sheet read for 3 minutes" exist.

The Feedback and Testing tool lives inside askdnd

Plan the boundary
app/fft (8,400 lines, 5,000 of tests), scripts/feedback.py · boundary small to medium · lifting it out large
Why it was built this way

Quick to build: it borrowed sign-in, the live connection and askdnd's pages.

What I'd do now

First a hard boundary: its own part of the database and a small adapter for people and settings, so it never reaches into the game's code. A separate service only when a second project needs it.

What shows it hurts

44% of commits since Nov 17 touch it, and each redeploys the game and runs the game's full tests. The game-night freeze is switched from inside the app it freezes. You want it reusable, and today it can't be lifted out.

A character sheet is a loose bundle of values

When nearby
app/ddb.py, ddb_sheet.py, character_views.py · large if all at once
Why it was built this way

D&D Beyond's data is large and shifting; a plain dictionary was quickest to start with.

What I'd do now

A typed sheet that askdnd's one reader produces, its parts converted as each is touched. A value D&D Beyond renames then fails loudly in a test, not quietly as an empty box.

What shows it hurts

The reader is on its 32nd version in five weeks; about 250 functions take the sheet with no shape; a renamed key shows as nothing rather than an error.

Smaller ones, done when we're in that code anyway

  • Who's asking is looked up once per request, on a thread, so the special second database connection (the Nov 8 fix) can go.
  • Play state that changes every turn (conditions, concentration, a fight) in rows of its own, so it stops locking the character row (a deadlock on Oct 29, doubled reminders on Nov 2). The VTT's fight tables already intend this.
  • The Feedback tool's rules file (2,645 lines) split by what it governs, still with one door in.
  • Board order written once: Claude's own work order is computed twice, and the two disagree about a Roadmap build with no plan yet (found by tonight's review).
  • Background jobs' mail-sending and locking written once (copied three times today).
  • Now and then, after a backup, remove tables nothing has read for 30 days: today's rule only ever adds.

Built well: keep exactly as it is

  • One service, one database, pages drawn on the server. Right for five people; none of the changes above needs Redis, a front-end framework or more services.
  • The live connection. A message only says what changed; the page fetches it through the normal checked routes, so nothing private travels on it.
  • The D&D Beyond bridge's shape. Queue a change, make it in the player's own tab, read the sheet back, never overwrite a number D&D Beyond changed meanwhile: the right shape for an unofficial service.
  • Who may do what, in one place, with every route tried by every kind of person in the tests: unusually strong for an app this size.
  • The privacy design. Transcripts filtered on your Mac, kept only encrypted in storage, Claude given first names, hidden entries hidden everywhere by one rule.
  • Operations. Nightly backups with a tested restore, a staging copy, deploys that check themselves, Sentry.
