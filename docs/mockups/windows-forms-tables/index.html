Roadmap item 47 · a mockup with picks

Windows, forms and tables, one way everywhere

“It seemed like we had a lot of UI problems in the most recent round, we should fix these holistically and check other areas for similar problems. I am surprised these were not caught in testing or the review.”

Your round on Backstage found eleven of these (issues 119–126, 129, 131, and 121's “evaluate all of these new modal layouts”). They have one cause: windows, the fields in them and stacked tables are each built several ways, and nothing checks them. Below: why the checks missed them, three choices drawn on your own windows, the fixes that need no choice, and what the checks become.

Why testing and the review missed them

Windows were never openedThe layout tests and the before-and-after pictures open pages, and only one window (the Spell Book). The windows Backstage's rounds 2–4 made on Nov 24 (the item builder, History's windows, Feature use, the house rule) were never opened by a check.
Most were spacing, not breakageOf your eleven, only one is something on top of something else (131: damage types spilling under the next row). The rest are uneven gaps, Save in the wrong place, buttons stacked, two header rows. No check reads “is this the same as everywhere else”: only one shared piece can promise that.
Three ways to build a window45 windows: 21 have a footer, 24 don't, and the large ones grew from pages, so Save sits wherever the page ended. Fields come in three layouts (label above, beside, in a grid), sometimes inside one window.
The review reads codeThe code review reads the change's text. The pictures compare before with after, so a brand-new window has no before, and nothing opened it to take one.
And my own lookFour rounds merged in one day, and I looked at the pages, not every window and every state. That's the part the checks below can't replace, so it gets a written list.

One check is already fixed today: the layout check only looked for overlaps in the menu bar and small badges; it now asks what's drawn over every line of words, on a page and in an open window. Running it over every page and window (52 windows, as admin, DM and player) found no new overlaps, which matches the above: the rest is design.

W1 · Where a window's Save goes

Every window gets the same three parts: its head (what it is, its name, ✕), its body, and its foot, which holds Save and Cancel, with Remove or Retire at the far end. The choice is whether the foot stays at the window's bottom edge while the body scrolls, or comes right after the last field. Drawn on New item (issues 119, 120).

What the checks become (in scope, no choice needed)

  • One window piece, one field pieceEvery window is built from the one window (head, body, foot) and every field from the one field (name, box, help, error). A test fails on a window or a form built any other way, the same way tests already fail on a hand-made count pill.
  • Every window opened by the testsThe layout tests open every window each page opens, as each person, at laptop and phone widths, and run every layout check on it, the new “covered” check included.
  • Every window in the before-and-after picturesSo a new or changed window shows up in the comparison I look at before merging; a brand-new one is listed as new for me to look at.
  • Buttons that stackA new layout check: two buttons of one row sitting one above the other while they'd fit side by side (126).
  • My look, written downBefore a change people see merges, I open each window it touches and note in the pull request what I looked at: Save in the foot, one field layout, one gap, errors under the box, nothing under anything.

How it's built: first the pieces and the checks, in one change. Then each Product Area's windows move onto them, one pull request per area (Backstage first, as your round found it), each one you try once. A window not moved yet is listed by the test as work left, so nothing is forgotten.
