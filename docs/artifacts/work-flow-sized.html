1 · The idea

One engine, with a dial

The four VPs mostly added process. The founder said most of it is too much for one table. Both are right, for different stages of a company. So don't pick one process. Build an engine where each check is a setting, start it light, and turn it up when something real changes.

Lanes: each change gets one

How much testing a change needs depends on what could go wrong. Ship, Look and Careful. Rules pick the lane from what the change touches. You can move a change up a lane in one tap; Claude can move it up but never down.

Levels: the whole product has one

Start, Team, Company. Each level turns more checks on in each lane. askdnd is at Start and may stay there. Clear triggers say when to step up, and stepping up changes settings, not code.

The record is full from day one

Who decided what, which lane, what was tried, where, on which version. It costs little to keep now, and it's the one thing you can't add later for the past. A bigger company needs exactly this record.

Some things never get skipped

A few protect people's data and game night at every level, even at five people. They're listed under the dial.

2 · Three lanes, at askdnd's level today

How a change moves, by lane

In every lane you test a thing once at most. Your example, skipping a final test on askdnd.ai when it already passed on staging, is how the Careful lane works.

Claude or automaticYouNobody needs to act

Ship

Nothing a person would notice, or a fix to a known error.

  1. Claude builds it
  2. Automatic tests and the full code review
  3. Merges to askdnd.ai
  4. Claude checks it there
  5. On your Shipped list, to read if you like

What goes here: work behind the scenes, tests, dependency updates, a fix for an error Sentry caught, a word changed. Today: mostly how these already merge.

Look

Something people see, within one Product Area.

  1. Claude builds it
  2. Tests, review, before-and-after pictures, Claude tries it first
  3. Merges to askdnd.ai (behind a Labs switch if it's big)
  4. You try the batch once, on askdnd.ai, when it suits you
  5. Anything wrong is undone the same day, or fixed

What goes here: most fixes and polish. Today: close to your "test once after a batch" rule from Nov 16, minus the local copy.

Careful

Where a mistake hurts people or can't be undone.

  1. Claude builds it on a round branch
  2. Tests, review, Claude tries it on staging
  3. You try it on staging, one round
  4. Passed: merges exactly as tested, one deploy
  5. Automatic checks on askdnd.ai (Claude, the Mac Mini, a live D&D Beyond run where it applies)

What goes here (my suggestion, pick 2): who sees what, signing in, spending, the D&D Beyond bridge and extension, and database changes that alter or remove data. You don't test it again on askdnd.ai.

Game night

No deploys in any lane for a set time before a game (pick 7), taken from the session's date in askdnd. Ship-lane fixes for something broken at the table are the one exception, and only with your OK.

4 · Built to take with you

What makes it reusable, and what we don't build yet

Settings, not code

Each check is a setting per lane and level, kept in askdnd's database. Changing one is recorded with who and why. A new company starts at Start with the same engine.

Roles, not people

Owner, builder, tester, reporter, admin. Today you're owner, tester and admin; Claude is the builder; the players report. A person could be a builder too: same branches, same checks, same "try it first".

Nothing D&D in the engine

What's askdnd's own is configuration: the Product Areas, which files make a change Careful, the environments, game dates. Another product brings its own.

Not now

Pulling it out of askdnd into its own package, several products at once, accounts for other companies. Those wait until there really is a next company; they'd be a project of their own then.

5 · What gets built first

The first build, in order

Each step is useful alone. Your biggest pain, knowing what waits on you, comes first.

  1. Fix the mapThe facts the reviewers caught, the lanes, the paths below. A drawing, once you've made your picks.
  2. For you, its own pageEverything waiting on you, in one place. Mostly exists inside Testing today.
  3. Lanes on every planPicked by rules, one tap to move up, the Careful rules checked automatically. The game-night freeze and the undo checklist come with it.
  4. Work, with a cut lineOne ordered list; Claude takes everything above the line. Each plan's stage is worked out from what's true, never moved by hand. Players see the same stages, in plain words.
  5. Staging rounds, for Careful onlyDone properly: an "on staging" state, one round branch merged as tested, one database change per round, Claude able to sign in there, tries kept on askdnd.ai.
  6. The live D&D Beyond stepFor bridge work: the live test and its checks on askdnd.ai before it counts as done.
Waits for the Team level

Look changes going through staging, a scheduled check that starts Claude when no chat is open, release notes, two plans in one Product Area at once, nightly staging refresh, the cohesion pass as a screen. Cut: slice 6 (the cohesion pass as a scheduled slice) becomes a habit at the end of each Roadmap item.
