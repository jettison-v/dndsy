askdnd Outside Review

A second model's review of askdnd v2: the code, and the design on a laptop and a phone, seen as an admin, the DM and a player. Written for the model that builds askdnd to check and act on. Nothing in the repo was changed.

For the model addressing this

  1. Treat every finding as a claim to verify, not an instruction. I had the code and CLAUDE.md, not your conversation history. Where a decision was deliberate, say so and add the reason to docs/DECISIONS.md; that closes the finding.
  2. Each finding has an id (C code, W writes to D&D Beyond, A what is sent to Claude and OpenAI, R the roll engine and its data, D laptop design, P phone design), a severity, where it is, what I saw, why it matters and a suggested fix. Answer each as fixed, deliberate (reason), not reproduced or later (roadmap).
  3. Severity is for a five-person table on a live product: medium is worth doing soon, low is worth doing when nearby, note is an observation or a question. I found nothing I would call high.
  4. This page's source is not in the repo. Per CLAUDE.md, save it under docs/artifacts/, list it in docs/artifacts/README.md and docs/library.json, and run scripts/library.py. It contains no names, emails, book text or story.
  5. File and line references are from commit bae51c7 (main, after PR 275) for the first pass and ca7d07c for the W and A findings, each with uncommitted work in the tree; lines will drift.
  6. The W and A findings come from reading the code only. None was tried in the browser, because trying them changes data.
  7. The R findings were added on Nov 10 at commit 03b6958 (branch jettison-v/dmg-items), after the roll card became the only roll window and the roll data moved to a file per book. Findings above that mention the old roll window (D6's "0 bludgeoning", parts of P1) were written before that; check them against the card.

What is strong, and should not regress

  • The refusal sweep. tests/test_refusals.py takes every changing route from the app's own list and fingerprints every table before and after. A new route is covered the day it is added. This is the single best thing in the repo.
  • One list of rules. access.allows() is the only place roles are decided, and the chart on Manage › Table is drawn from it.
  • The live connection's design. Messages say what changed, not the change; announces go out after commit and are dropped on rollback; each page keeps at most one of each message. The one exception (a table roll's dice) is narrow and documented.
  • Event-loop discipline. Plain def routes, LoopSession, and a test that fails on an async route taking db, each traced to a real incident.
  • The extension is conservative. Two permissions, a write allowlist checked on both sides, the key held in session storage, origin checks on the messages that matter, only followed games reported.
  • The bridge's engine. A change is refused up front when the sheet can't be reached; what a page asks for is checked against the sheet (_change), with limits worked out from the sheet and never the page; the extension compares each value just before writing; askdnd counts a change only after reading it back; a Give removes the giver's copy only once the receiver's exists. Coins are all-or-nothing and the Undo for them is validated (coins.checked).
  • What leaves for Claude and OpenAI is narrow. Players' private notes are never gathered. Narration sends only a published recap's words. Drawing sends only the description, the style and its pictures. Every call checks the spending limit first. The transcript is kept in file storage, not the database.
  • Privacy held everywhere I pushed. As the DM, a player's Plan tab is absent and its address forwards to Sheet; pins and reminders are not drawn. As a player, Manage answers 403 with a plain message. Sentry scrubbing, the document sandbox and back_to() are careful.
  • Escaping. The roll window and corner cards build HTML by hand but pass every value I traced through esc.
  • Battle's shape. Action, Bonus Action and Reaction as columns, pins on top, resources as pips. It matches how a turn is thought about.
  • Words. Empty states, refusals and status lines are plain and specific ("Manage is for the DM, reviewers and admins").

Code findings

C1medium

Ordinary pages send no browser security headers

Where
app/main.py (no header middleware). Only documents.py, files.py and one feedback route set any.
Seen
No Content-Security-Policy, frame-ancestors or X-Frame-Options, X-Content-Type-Options or Referrer-Policy on HTML pages.
Why
askdnd can change a real D&D Beyond sheet through the bridge. Another site can frame askdnd and trick a click (SameSite=Lax does not stop framing of a top-level navigation in every browser path), and any escaping slip has nothing behind it.
Suggest
One middleware: frame-ancestors 'none', nosniff, Referrer-Policy: same-origin now. Then a script policy in report-only mode (pages have one inline script in base.html, so it needs a nonce), reported through the existing /errors/page path, enforced once quiet.
C2medium

HTMX is loaded from unpkg.com with no integrity check

Where
app/templates/base.html:18; Google Fonts on line 16.
Why
Every button that saves depends on HTMX. If unpkg is slow or down on game night, the app is read-only; if the file there were ever altered, it runs with each person's session. The dice library is already vendored, so this looks like an oversight.
Suggest
Put htmx.min.js in app/static/vendor/ and serve it with static(). Fonts can stay (they use display=optional) or be self-hosted for the same reason.
C3low

/bridge/delivered doesn't check whose batch it is

Where
app/ddb_bridge.py, bridge_delivered (about line 1447). Compare bridge_outbox and _intent_of, which do check.
Seen
It calls _signed_in only, then delivered(db, batch_id, …). Any signed-in person can report any character's batch as made, failed or conflicting. fresh_read does refuse their sheet data.
Why
The read-back from D&D Beyond decides the outcome, so the worst case is a batch replanned, retried or stopped by someone else. Small, but it is the one changing bridge route without an ownership check, and the refusal sweep can't see it (the batch id it tries is not in state "sending").
Suggest
Require picks.can_edit for the batch's character, or the campaign's DM when it was offered by="dm", or an admin. Add a case to the refusal tests with a batch that is "sending".
C4medium

All page behaviour is one 340 KB script and one 329 KB stylesheet

Where
app/static/app.js (5,081 lines, lines up to 438 characters, one closure, 242 listeners), app/static/app.css (3,649 lines, 181 over 200 characters).
Why
The Python side has a linter, 92% coverage and small functions (10 of 1,843 over 80 lines). The browser side has none of that: no linter, no unit tests, and it holds real rules (measuring a move, areas, the roll card's steps) mirrored by hand from Python. Browser tests cover flows, slowly. This is where a silent regression is most likely, and every edit makes a model re-read a very large file.
Suggest
In order of value: (1) add a JavaScript linter to the Server tests job, errors only at first; (2) split by the section headings the file already has into ES modules loaded with type="module", no bundler needed; (3) for logic mirrored from Python (measure, areas), one shared table of cases run against both sides. Split the CSS the same way, by component.
C5low

Light static checking; modules import each other in circles

Where
pyproject.toml (select = ["F"]); 303 import statements inside functions across app/.
Why
Only unused and undefined names are caught. Imports inside functions are how circular dependencies are being worked around (web ↔ ddb_bridge, table_rolls ↔ hiding, initiative, table_fight…), so a broken import shows only when that line runs.
Suggest
Add ruff's B (likely bugs) and UP rules, then a type checker on the pure-logic modules first (hit_points, measure, roll_plan, coins). Don't chase the cycles wholesale; when a module is next touched, move shared helpers down a layer.
C6low

Cross-site protection rests on the cookie's SameSite setting alone

Where
app/main.py (same_site="lax"); no Origin check on POST. The WebSocket already has one (realtime._same_site).
Why
Lax is a good default and probably enough. A second, cheap layer costs a few lines and removes the dependence on browser behaviour.
Suggest
Middleware: for POST, PUT and DELETE carrying the session cookie, refuse when Origin is present and isn't the request's own host. Exempt requests authenticated by X-Askdnd-Bridge, the upload token or the feedback key.
C7note

Several things assume one copy of the app

Where
ddb_bridge._health and _carry_read, errors._recent, admin_sessions.busy(), access.invalidate() (clears this copy's cache only; others catch up within 10 s).
Why
Fine today. During a deploy two copies overlap, and a second replica would make the bridge's health and the "Claude is busy" guard disagree between copies. The live connection and the unwatched-sheets loop were already built for several copies, so the assumption is uneven.
Suggest
Record "one replica" as a decision in docs/ARCHITECTURE.md with this list, so it is a known step if a second copy is ever added.
C8note

A roll's modifier, damage and label come from the browser

Where
app/table_rolls.py, make_roll: mod, dmg, label, adv are form fields, bounded by MAX_MOD and the formula parser.
Why
A player can send "Fire Bolt +12". Among friends this is the same trust as physical dice, and manual rolls need it. I expect it is deliberate; I didn't find it written down.
Suggest
If deliberate, one line in DECISIONS.md. Optionally mark a roll in Table rolls when its numbers differ from the character's roll plan, which informs the DM without policing anyone.
C9note

A feedback note can carry a player's private notes to an admin

Where
app/feedback.py, send: keeps the page's HTML and a picture of the screen.
Seen
A note sent from Plan, or from Battle with reminders showing, includes the things the campaign's DM must never see. The queue is read by admins.
Why
Only matters if an admin is also that campaign's DM, now or later. The rule "never the campaign's DM, even an admin" is enforced on pages and in View as, but not here.
Suggest
Either refuse to show a note's page and picture to an admin who is the DM of the campaign it was sent from, or confirm that the DM is never an admin and record it.
C10low

View as checks the DM rule only when it starts

Where
app/view_as.py: refusal() runs in start; viewing(), run on every request, checks only admin and "can sign in".
Why
An admin made a campaign's DM while already viewing as one of its players keeps seeing that player's notes until they stop. A narrow window, but the rule it protects is a standing one.
Suggest
Have viewing() return None when refusal(real, target) is non-empty. Roles are already in memory, so it costs nothing.
C11low

No sweep for reading, to match the sweep for changing

Where
tests/test_refusals.py covers POST, PUT, DELETE. tests/test_links.py opens pages as people who may.
Seen
I found per-feature tests of who can read what, but no test that asks every GET route, from the app's own list, as someone who must not read it (signed out; a member of another campaign; the DM for notes).
Suggest
The same harness: every GET with ids that exist, as another campaign's player, expecting 401, 403, 404 or a redirect, with an explicit list of pages any member may read. If this exists and I missed it, ignore.
C12low

The least-tested files are askdnd's own table

Where
Branch coverage: drawing.py 69%, table_page.py 75%, places.py 79%, table_fight.py 79%, entities.py 80%, tokens.py 83%, scene_notes.py 84%.
Why
The total (92%) hides that the piece heading for a one-time cutover is the thinnest. Hidden tokens, fog and the DM-only scene notes are visibility rules.
Suggest
Before the cutover, bring these to the level of the rest, starting with what a player's page must never receive.
C13note

Settling a batch sleeps on a worker thread; drafting runs inside the web server

Where
ddb_bridge.delivered: up to three time.sleep(1) between read-backs after taking _lock. admin_sessions: drafts on daemon threads.
Why
Both are understood trade-offs (the first follows a real D&D Beyond quirk; the second is handled by "Interrupted, draft it again" on restart). They are the two places a busy night and a deploy interact. Worth a line each in ARCHITECTURE.md so they aren't rediscovered.
Suggest
No change needed now. If drafts get longer, don't deploy while busy(), or let deploy_check.py warn.
C14note

Some foreign keys have no index

Where
app/models.py: about 30 foreign-key columns without index=True (some are covered by a unique constraint or a composite index I didn't trace).
Why
Irrelevant at one table's size. It matters for deletes that cascade and for per-campaign queries if campaigns multiply.
Suggest
Nothing now. Check table_rolls by campaign and bridge_intents by character first if a page ever feels slow.
C15low

CLAUDE.md is 12,900 words and loaded into every session

Why
It is an excellent record, and it is also the project's largest single point of drift: one paragraph per feature, each several hundred words, edited by every change. It costs tokens on every turn of every session and makes "what are the rules" hard to separate from "how does feature X work".
Suggest
Keep in CLAUDE.md only what must hold in every session: working with the owner, privacy and product rules, conventions, the before-done checklist, and a one-line index of areas. Move each "Where things are" paragraph to docs/areas/<name>.md, read when that area is touched. A test can check every app/*.py is named in exactly one area file, as test_deploy.py does for watch paths.
C16note

Correction to my first pass: no paid action is reachable by a plain link

Seen
My first summary to the owner said re-recording a narration could be triggered by a GET. That was wrong: narrate_route is a POST. The ten GET routes that commit only keep bookkeeping (what was seen, a narration's measured length, the bridge going to sleep).
Suggest
Nothing to fix. If you want it guarded, a test that no GET route changes a table outside a small bookkeeping list would mirror the refusal sweep.

Findings: writes to D&D Beyond

W1medium

A fast double press on Apply can take the damage twice

Where
app/templates/_hp_form.html:2 (the form posts to /hp/apply with no hx-disabled-elt or hx-sync); hit_points.apply.
Seen
Each apply adds a relative change ({"amount": -N}). From a roll, a second apply is refused only once the first has committed (applied() is checked, then inserted, with no lock or unique index). From − and + on the tile there is no roll, so nothing refuses a second one at all. Enter takes the form, and the window closes only when the answer arrives.
Why
Two Enters, or a double tap on a slow connection, is 2×N on the real sheet. The item window disables its buttons on send and the World forms use hx-disabled-elt, so this form looks missed.
Suggest
hx-disabled-elt="find button" and hx-sync="this:drop" on the form. For the roll case, a partial unique index on table_rolls (parent_id, character_id) where kind = 'applied'. A browser test that submits twice quickly would hold it. The same check is worth a minute on the creature Hit Points form.
W2low

Some Undo cards send back state the server stores without checking it

Where
casting.undo_cast → companions.uncast (the companions form field is parsed as JSON and merged into Character.companions) and companion_story.restore (the story field replaces Character.creature_story).
Seen
The undo payload is made by the server, held by the browser, and trusted on the way back. Only the character's own player can post it. Any JSON object is accepted: values of the wrong shape would then be read by Battle, Party and the fight for everyone at the table. In two posts a player can also set a story whose made names another entry, then undo with that id: restore deletes it if it is a Creature entry in the campaign with no summary and nothing added. That is a narrow case, but it is a delete reached through client-held state.
Suggest
Sign the undo payload (itsdangerous is already a dependency) or keep it server-side under an id, as a short-lived row. coins.checked is the model where the payload must stay in the browser.
W3low

A character's portrait address is fetched by the server with no host check

Where
app/drawing.py, _portrait → _read(url).
Seen
The address comes from the parsed sheet. Since extension 0.9.9 a sheet can be the JSON a player's browser sends (ddb_bridge.fresh_read), so a player can make it any address, and the server will request it when someone draws with that portrait as a style picture.
Why
A blind request to an address of the player's choosing from inside Railway. Low among five friends. fight.py and giving.py already allow pictures only from D&D Beyond's own hosts.
Suggest
The same host allowlist in _read, https only, no redirects to other hosts.
W4note

askdnd's half of a cast stays when the D&D Beyond half doesn't go through

Where
casting.cast: the slot is a bridge change; Concentration, a familiar or a summon are set on the character in the same request.
Seen
If the slot change later stops ("Didn't go through") and is undone from the card or the Live window, ddb_bridge.dismiss only marks that change. Concentration and the creature stay. The cast's own Undo handles both, but only from its corner card.
Suggest
Probably right under "remind, don't automate". If so, have the stopped change's card say what askdnd still shows ("still Concentrating on Bless"). Verify I read the flow correctly.
W5note

A Short Rest's "at least 1" is applied to the total, not to each die

Where
rests._make: at_least = max(row.total, number of dice), from one formula such as 2d8-2.
Seen
The 2024 rule gives each Hit Point Die's roll plus Constitution a minimum of 1. With a negative Constitution modifier, dice of 1 and 6 heal 1 + 5 = 6 by the rule and 5 here. Only characters with Constitution under 10 are affected.
Suggest
Roll each die as its own part and floor each at 1, or note it as known in docs/rules/.
W6note

More places that trust the player's browser, to record with C8

Seen
A private death save posts its own result (POST /characters/<id>/death with result=nat20 brings the character back with 1 Hit Point on D&D Beyond). The sheet as the extension read it is kept as the character's copy. An item Undo posts how much healing to take back. Each is limited to the player's own character.
Suggest
The same answer as C8: if this is the table's trust model, say so once in DECISIONS.md so later reviews stop raising it.

Findings: what is sent to Claude and OpenAI

A1medium

Regenerate description on a hidden entry sends that entry to Claude

Where
app/templates/_entity_body.html:52 offers the button whenever can_edit; entity_pages.regenerate → entities.regenerate → build_describe_messages, none of which looks at the entry's status.
Seen
For an entry with status draft (hidden), its name, summary, aliases and merged facts go in the request. CLAUDE.md's rule says a hidden entry, its facts and relationships "never go to Claude (drafts, questions, suggestions, descriptions, conversations)". The standing-rule test checks describing another entry, not the hidden one itself.
Why
It takes the DM or a reviewer pressing the button on their own secret, so it may be meant. As written, the code and the rule disagree.
Suggest
Refuse in entities.regenerate when the entry isn't published and hide the button, with a line saying why; or amend the rule to "unless the DM asks for it herself". Either way add the case to test_a_standing_rule_a_hidden_entry….
A2low

A key moment's own words can still name a hidden entry

Where
tests/test_extraction.py, the last assertion of the standing-rule test: "Veiled Duke</a>" not in page. entities.moments feeds moments' text to build_describe_messages.
Seen
The test proves the name isn't a link. Its docstring, and CLAUDE.md, say the name never shows on a key moment. I found no code that drops or masks a published moment whose text names a hidden entry, on Story or in what Regenerate sends for the other entries that moment mentions. I did not trace every template, so verify.
Why
A recap drafted from a transcript where the DM said the name aloud will contain it; the reviewer's read before publishing is the only gate.
Suggest
Decide which is true and make the test say it: either hold back a moment linked to a hidden entry until it is shown (the link row already exists, EventEntity), or reword the rule to "never linked, and the reviewer checks the words".
A3low

The drafting prompts are written for one table, in code

Where
extraction.SYSTEM_PROMPT and build_messages: "four players and a Dungeon Master who play over Zoom", the owner by first name as the reviewer, "the notes are written from one character's point of view", and <clarifications_from_…> tags carrying his name.
Why
Campaigns, roles and reviewers are per campaign everywhere else. A second campaign, or the DM reviewing, gets a prompt that states the wrong reviewer and the wrong narrator. It also puts a person's name in a public repo's source, which the repo's own rule asks to avoid for the table (the owner's may be an accepted exception).
Suggest
Fill these from the campaign: the reviewer's name from who pressed Draft, the point of view from the notes source's character, the table's size from its members. Use role words in the tags.
A4note

Every draft sends each player's real name and the DM's

Where
extraction._known_world: "Dungeon Master: name" and "Player characters (character — player)", the player being player_name or, without one, the name on their Google account.
Why
It helps map a transcript's speaker labels to characters, and nothing in the privacy rules forbids it. It is the one piece of personal data that goes out on every call, including conversation.check and the cheap revise pass that has no transcript to map.
Suggest
Record it as intended, or send first names only, and leave players out of the passes that don't read a transcript.
A5note

Usage prices a call as Opus whichever model answered

Where
extraction.MODEL, PRICES, _cost; calls pass fallbacks="default" and _usage records response.model.
Seen
The model that answered is kept on the run, but the cost is always worked out with one price table. The spending limit is checked before a call and can't see that call's size, which is fine at these amounts.
Suggest
A price table keyed by model, falling back to the dearest when the model is unknown, so the limit errs on the safe side.

Findings: the roll engine and its data (Nov 10)

What was reviewed. The Roll Data Review page (docs/artifacts/roll-data-review.html) against the code: rules_book.py and roll_plan.py in full, the four files in app/data/rules/ by script, scripts/roll_audit.py and rules_from_books.py in part, tests/test_rules_books.py. All 91 Player's Handbook feature, feat and species entries were read against the 2024 rules from memory, not against the book.

What held. 360 roll-engine server tests pass and ruff is clean. tests/browser/test_every_roll.py and test_roll_card.py: 23 passed, none on a second try. Running scripts/roll_audit.py rewrote roll_recipes.json byte for byte, so the compiled file matches the book files today. In the 91 entries I found no wrong dice, scaling table or save ability. On a party Sheet all 36 roll buttons carried a plan and the card opened beside its button. The shape (rolls, adds, when, to, with, book-level scales) is a real improvement on four code paths, and the direction is right.

The short version. The page's "Built · Done" card says more than the code does. The parts of its own recommendation that would prove coverage are the parts not built. Build those before filling in more of the books.

R1medium

"Done" isn't the whole Player's Handbook

Where
app/data/rules/phb-2024.json: 76 features, 10 feats, 5 species traits, 39 spells. dmg-2024.json: 8 items.
Seen
The page says class and subclass features, species traits and feats "that roll or add a number" are in. None of these appear in the book files, class_rules.py or the compiled recipes: Cutting Words, Bend Luck, Portent, Cosmic Omen, Agonizing Blast, Potent Spellcasting, Disciple of Life, Psi-Bolstered Knack, Homing Strikes, Fanatical Focus, Death Strike, Mantle of Inspiration, Protective Field, Bastion of Law, Overchannel, Wholeness of Body; the feats Poisoner, Chef, Healer, Piercer, Heavy Armor Master, Telekinetic, Inspiring Leader, Boon of Recovery, Boon of Irresistible Offense; the spell Chaos Bolt. "169 spell recipes" is the total across every book, not the PHB's spells beyond the SRD.
Why
Agonizing Blast and Potent Spellcasting change the commonest roll a Warlock or Cleric makes. A table that isn't this one would meet these on its first night. The list is from my memory of the book, so treat it as examples, not the full gap.
Suggest
Change the page's card to say what is in (counts per kind) and that coverage is unmeasured until R2 exists. Then fill from the report, not from memory.
R2medium

Nothing can show what a book still lacks

Where
The page's recommendation 6 and "Then the books" step 4. scripts/roll_coverage.py covers the party's sheets only.
Seen
No coverage report over the books, and no made-up character per class at levels 1, 5, 11 and 17 in the every-roll test. test_rules_books.py checks each entry's shape, which is good, but not that a book's rules are present or played.
Suggest
Build this next, before more entries. From the offline books, list every feature, feat, trait and item whose words hold dice, a save or a bonus to a roll, and mark each as rolled, in words on purpose (with the reason), or missing. Commit only names and statuses. The made-up characters then play what the report says is rolled.
R3medium

A non-spell feature's save DC isn't in the data

Where
roll_plan.plan: a save with no dc takes "DC n" from the option's words, else _spell_dc(sheet). Only four rolls in the book files carry dc, all items.
Seen
With no words: Elemental Burst, Deflect Attack: Redirect Attack, Breath Weapon and Boon of Energy Resistance got DC 12 on a Monk 6 / Warlock 2 (the Warlock's spell save DC; the rules give 8 + the feature's own ability + Proficiency Bonus). With no spells at all the DC is None and _judge still says "ready". On the party's real sheets D&D Beyond's words supply the number (Redirect Attack: 14), so nothing is wrong at the table today.
Why
The made-up characters of R2 have no D&D Beyond words, so they would play wrong DCs and pass. So would any feature whose words D&D Beyond writes as a formula.
Suggest
Put dc on each such roll as a token ({dc:dexterity}, {dc:constitution}; a spellcasting feature can say spell). Prefer the data over the words. A plan with a save and no DC is a gap, not ready.
R4low

Half the recommended entry shape isn't there

Seen
No entry has an id or a D&D Beyond id. checked is on 24 of 241. Entries are found by display name through four cleaners that differ slightly: rules_book._norm, the lambda in roll_recipes.feature, roll_recipes.item (lowercase, strip "Use an item: ", cut at " ("), and class_rules._norm. That is the page's own problem 5, still open. rules_book.active(sheet) never sees the campaign, so a DMG item's rules apply whether or not the campaign lists the book (problem 6).
Suggest
One norm() used everywhere now. Ids when the next book is added, with the D&D Beyond definition id where the sheet gives one, so a 2014 and a 2024 thing of the same name can't collide. Pass the campaign's books to active for item entries.
R5low

The engine still plays the old shape, compiled from the new one

Where

Small points in the entries

Battle's columns start more than two thirds of the way down the first screen

Seen

The most-pressed controls are too small for a thumb

Seen
On Battle, 24 of 75 visible controls are under 32 px in one direction. Hit Points − and + are 24×24. A reminder's × is 21×19. "+ Add" is 22 high. The common actions (Dash, Dodge, Hide…) are 26 high and sit close together. ↗ and ⓘ by the name are 24×24.
