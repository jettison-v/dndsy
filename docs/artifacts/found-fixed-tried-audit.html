Audit · Nov 17 · Found, Fixed, Tried · devil's advocate

Found, Fixed, Tried: the audit

Three independent reviewers read the brief, the screens and the code askdnd runs today, each told to find what's wrong, not what's right: one on architecture and a company's needs, one on workflows and design, one on the live code. I added what only tonight's session knows, and checked each main claim in the code before it went in.

Verified means I confirmed it in the code or the mockup. Plausible means the reasoning holds but I didn't reproduce it. Migration is left out at your word: a clean rebuild is fine.

The verdict

The direction holds: one model, Testing for your work, Feedback as the record, the developer can be Claude. But it isn't ready to build. Before building, the model needs three more pieces (a try's context, a check's versions, questions as their own thing), one written table of how every state changes (the screens contradict themselves in five places), a trust and privacy layer designed in (two of your standing rules are broken in the code today), and about a dozen missing workflows. The design should colour by whose turn it is and use far fewer state words. And some things should be cut: two-way sync with Jira, parallel area chats until their groundwork exists.

A · Fix now, separately

Two standing rules are broken in the code today

Not part of the redesign: these are on askdnd.ai now, and your rules come first. One small change, with tests that guard each rule.

Critical

A player's words reach Claude before you approve them

Verified

When a player answers "Still broken" on Notes you sent, their words go straight into Claude's inbox, while the note itself waits for your approval (app/your_notes.py). Claude's API also lists notes still waiting for approval, and returns a player's not-yet-approved Add to it in a note's thread.

the inbox says only that its sender says it's still broken (waiting for you); the API refuses notes and thread lines you haven't approved; a "standing rule" test checks every way Claude reads.

Emails, full names and private pages reach Claude

Verified

Claude's API returns each note's full context, including the email of whoever was viewing as, the sender's full name, and the whole page as it was drawn, which can hold a player's character notes. Your rule is first names only, and character notes never to the DM; anything Claude writes from that page (a title, a check) can carry it to an admin who is the DM.

first names only, no emails, and no page HTML to Claude unless you open it for a note; the reading tests (tests/test_reading.py) extended to Claude's API.

Architecture reviewer 1

B · Architecture

What the model and the system need

Critical for a company

Untrusted words steer an agent that can ship to production

Plausible

Approval screens a report for relevance, not for instructions hidden in it, and Claude also reads the page captured with it (up to 3 MB, including text from D&D Beyond). The proposed area chats would start from briefs built from that same material. For askdnd the risk is small (four players you know); for a company with outside reporters it's the first thing a security review asks.

label everything Claude reads by source; no page HTML by default; a change prompted by anyone other than the owner waits for a person to merge it.

Architecture reviewer 1

High

One key does everything, everywhere, and the staging relay can pose as you

Verified

Claude's one key works on askdnd.ai, staging and the Mac Mini, and can set any note or check to any state, passes included. Notes relayed from staging take the sender's email from the request, so a relayed note "from Brett" skips approval. Code running on staging (any branch with an open pull request) has that key.

a key per actor and environment, each allowed only what it does (staging may only submit, and its notes always wait for approval); Claude's key can't record a pass that verifies a fix.

Architecture reviewer 2

High

Three pieces are missing from the model: a run, a check's versions, a question

Verified

Every test tool has a run (who tried it, on what device, on which deployed version). Without one: a pass on your laptop hides a fail on Big C's iPhone; a round on staging is erased by the next staging refresh; a fix that was rolled back still counts as live. Checks are edited in place today, so an earlier Failed points at steps nobody saw. And a question can only live inside one note's thread, the latest hiding the one before. That's why tonight's six picks had to be pinned to unrelated notes.

add a Run (tester, device, deployed version), pin each result to the check's version, keep a check's state per device, and make Question (and a mockup's verdict) a thing of its own, answered in askdnd.

Architecture reviewer 4, workflow reviewer 5, my pass

High

The state rules contradict themselves in five places

Verified

"A check's state is its latest result", yet To try and Try again aren't results. "A check never closes an issue", yet Passed closes its issues as verified, and one issue can sit on two checks (A passes, the issue closes, B still fails on it). Results are "never changed", yet Change result changes the latest. "Problems found while trying land in that area", so an area grows every round and never finishes. An issue merged into one in a later area leaves its check stuck, and "one area at a time" stalls.

one written table of every state change, tested by trying every combination; a check's word worked out from its runs and its issues by rule; an area is done when its own issues are verified, and new finds are split out to the next one.

Architecture reviewer 5, workflow reviewer 7

High

History isn't truly kept, and two people writing at once lose one

Verified

A note's thread and a check's history are lists rewritten whole on every change, with no lock: your answer and Claude's reply landing together drop one of them. Tonight's Undo trims history. A stale tab can move a check from any state to any other. There's no single record of who did what; an admin's action is written as "Brett" whoever did it.

one append-only record of events (who, what, from, to), with every state worked out from it; each mark says which state it was made against and is refused if that's stale; a key on each send so a retry doesn't make two. Private words stored so they can be erased (privacy law) without breaking the record.

All three reviewers

High

A failed check gets stuck, and a done note makes a duplicate check

Verified

Only "done, with a PR" moves a failed check on, so a check whose issue is closed, deleted, put off or re-sorted stays Failed for ever, and its area never reaches Done. And replying on a done note whose check already passed makes a second check for it, bringing back something you passed.

every way an issue can end moves its checks by rule (a test for each); making a check is its own deliberate step, never a side effect of editing a note.

Live-code reviewer 2, 3

High

Claude's inbox can't serve two chats, and can skip an item

Verified

One read mark and one "listening" signal for all of askdnd: an area's own chat would mark the main chat's items read, and "Claude is listening" can't say which. An item can also be skipped when two changes save in the opposite order to their numbers. The "only one area at a time" lock is checked then set, so two chats can both take one.

a read mark per listener (and per area), marked read after acting; a lock with an owner and an expiry. These come before any area runs in its own chat.

Architecture reviewer 3, workflow reviewer 2

Medium

For a company: no workspaces, and two-way sync is the costliest, least distinctive part

Plausible

Everything is global (one queue, one read mark, one area lock), pictures need askdnd's campaign, live updates are per campaign, and "is the fix live" is decided by a script on your Mac. Two-way sync with Jira or Linear means mapping states like Claude asks onto every company's workflow, with merges, private comments and screenshots on both sides.

a workspace on every table and policy hooks in the adapter (who can see, redact, notify, store); a deploy notification instead of the Mac's script; treat an issue as a port that lives either here or in the company's tracker, with a link and export rather than two-way sync.

C · Workflows

What the screens can't do yet

High

A check that fails again after a fix has no right path

Verified

On a retry, Something's wrong… can only file a new issue, so the original stays Fixed and you file a duplicate. Nothing reopens an issue.

the window lists the check's own issues first ("Still happening"); picking one reopens it and sends it back to Claude. Add Reopen to a closed issue, and "came back" for one verified before.

Workflow reviewer 1

High

An unrelated issue holds a check hostage

Verified

Spot an unrelated bug mid-check and the only way to send it fails the check; if it's sorted into another area, the check and its area stay Failed until that area's turn. Partial or deferred fixes do the same.

the window asks "Does this stop the check passing?"; each issue can be moved to another area or marked "doesn't block this check".

Workflow reviewer 3

High

A round can't be stopped, and a blocker can't be flagged

Verified

The new card dropped today's End round, so it follows you to every page until the last check. Your rule allows a mid-round fix only for something that stops the round, but nothing lets you say so.

End round on the card (resume later from For you), and "This stops my round" in Something's wrong….

Workflow reviewer 4

Medium

Who confirms a fix is unclear

Verified

Passing closes issues and tells their senders it worked, yet a player's fix is that player's to confirm first. A check holding issues from you and two players has no single owner. The Mac Mini passing Claude's own fix is Claude confirming its own work.

confirm per issue, so "waiting for Big C" survives your pass; automated runs can fail a check but never confirm one.

Workflow reviewer 6

Medium

Can't try… does too many jobs

Verified

"On my phone", "needs a second person" and "not tonight" all send a good check back to be rewritten, and "blocked by issue 131" has no link, so it doesn't come back when 131 is fixed.

three choices: Later (stays yours), Blocked by… (linked to an issue; back when it's fixed), Check is wrong (to Claude).

Workflow reviewer 8

Also missing (smaller, all plausible)

  • Closing with the reporter told why: can't reproduce, works as designed, won't do.
  • Asking a reporter for more, and them answering, from Notes you sent.
  • Undo for approve, decline, merge and close; unmerge.
  • Moving issues between areas; renaming, merging, archiving an area (tonight left three empty ones).
  • Retiring a check; "fixed, no check needed" for something like a typo.
  • Re-trying passed checks after later changes (regressions), and the Mac Mini's failures added to the open issue.
  • When no Claude session is listening: say so on the send line, acknowledge the sender, and tell you.
  • Email when an idea ships or a note is declined or answered; a digest of For you.
  • For a company: severity, priority, assignment, two testers on one check, permission to change results.
D · Design and words

Colour by whose turn it is, and far fewer words

Medium

Over 25 state words, and they collide

Verified

"Claude asks" is an issue's state, an area's stage and the question itself. "Fixed" means Claude finished and also live. "Try again" means the fix is live or a result was withdrawn. Done, Closed, Passed, Shipped and verified all mean finished. Note, report, feedback, issue and problem name nearly the same thing. You've been confused by exactly this tonight (notes 114, 121).

every pill says whose turn it is, with one sentence beside it for the detail:

YoursClaude'sClosed

An issue closes with a reason (Works now, Won't do, Same as, Can't reproduce, Withdrawn). A check: To try, Passed, Failed, Blocked. An idea: Planned, Shipped, Declined. What anyone sends is a note; the work Claude does from notes is an issue.

Workflow reviewer 11, 12, vocabulary

Medium

Red means both "go" and "failed"; blue means both your turn and Claude's

Verified

▶ Try it and Done · next check are red beside a red ✗ Something's wrong…; Start round is a red title action, which the design system says is secondary; blue is To try (yours) and Fixing (Claude's); violet is Reminders' colour in the design system, and is used both for Claude's turn and your Mockup row; a green "Fixed" reads as done before anyone checked.

colour by whose turn it is (amber yours, violet Claude's, grey closed); failure keeps red, and the main action stays the design system's.

E · Cut or defer

What the reviewers would leave out

Cut

  • Two-way sync with Jira or Linear: a link and an export instead.
  • Change result's several targets: one correcting result, added, never an edit.
  • Five roles: three capabilities for now (report, test, develop), mapped later.

Defer

  • An area in a chat of its own, until per-listener read marks, a lock with an owner, and scoped keys exist; with one area at a time it gains nothing yet.
  • One reviewer would defer the Roadmap and idea voting too. You've asked for them next, so they're being designed separately (the Roadmap mockup), built on this model, not inside it.
F · What I recommend next

In order

  1. Fix the three rule breaks now (section A), as their own small change with tests. They're live and independent of the redesign.

  2. Revise the brief's model: add the run, check versions and questions; write the one table of state changes; the trust and privacy layer; colour by whose turn; the smaller set of words.

  3. Redraw the screens it changes: the card (End round, Still happening, This stops my round, Passed moves on), Something's wrong… (blocks or not, move to area), Can't try… (three choices), For you (everything your turn), the issue page (reporter's view, kept-from-you, Same as…), and the colours. Then your one verdict.

  4. Build in slices: the record of events and the five objects with their state table and tests first; then Testing's screens; Feedback's; the keys and the inbox per listener; and only then areas in their own chats.

The Roadmap with players' votes and comments is researched and drawn in parallel, on top of this model.
